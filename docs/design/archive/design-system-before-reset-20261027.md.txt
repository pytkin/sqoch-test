# Дизайн-система Sqoch — «Формуляр с разделами»

Статус: `accepted`. Владелец — проект Sqoch. 23 октября 2026 года пользователь
выбрал второй фактически показанный вариант Ideate — «Формуляр с разделами».
Commissioner, размеры текста/контролов и требования доступности
являются частью принятой системы.

## Полномочия и источник

Этот документ — единственный канонический владелец визуальных требований,
токенов, компонентов, адаптивности и состояний интерфейса. Перед изменением
пользовательской поверхности агент читает его по маршруту из [AGENTS](../AGENTS.md).
Изменение выбранного направления требует решения пользователя. Уточнение
отступов и текстов по проверенному UX-наблюдению сохраняет направление,
фиксируется здесь и проверяется на затронутых состояниях.

Функциональный [бриф](brief.md) сохраняет приоритет над растром и визуальными
решениями. HTTP API и архитектурные границы принадлежат
[технической спецификации](technical-specification.md). Задачи, фактические
проверки и ограничения — [плану работ](work-plan.md).

Текущий выбранный [референс](design/selected-formulary-20261023.png) сохранён
без изменения байтов. Исходный файл —
`exec-147f96b8-ec55-44b7-8e79-3da1453686ac.png`, размер — 1536×1024. SHA-256:

```text
0e9d88bde2224139ececaa72b5b245f691a3ed3cef668e4b4637b3ba124c4be1
```

Текущий растр задаёт редакционную композицию с колонкой названий разделов и
короткими полями/действиями. Числа ниже — принятые ориентиры реализации, а не
измерения пикселей растра; точные значения выражаются семантическими
CSS-токенами приложения. Генерация не доказывает точный шрифт, контраст или
адаптивность. Подписи концепции, демонстрационная доска компонентов и
служебные пояснения превью не являются частью приложения. Тексты ошибок и
бизнес-правила из растра не меняют бриф: для имени сохраняется требование
непустой строки после trim, новые числовые или иные ограничения не вводятся.

Необходимая граница поля немного темнее растрового `#8795A3`: исходная
пара с canvas даёт около 2,80:1, принятая — около 3,10:1. Divider не
используется вместо необходимой границы контрола.

Для обычного текста проверяется контраст не менее 4,5:1, для необходимых
нетекстовых границ и фокуса — не менее 3:1. Расчёт стартовых пар:
основной текст/white — 9,31:1, muted/white — 5,01:1,
muted/canvas — 4,58:1, white/primary — 5,53:1.
На цветных поверхностях проверяется фактическая пара: muted не переносится
туда автоматически. Цвет не служит единственным признаком ошибки, текущего
шага, ожидания или результата.

## Шрифт и типографика

Единственная выбранная гарнитура — [Commissioner](https://github.com/kosbarts/Commissioner).
Используется настоящий локальный файл с латиницей и кириллицей; лицензия
SIL OFL 1.1 хранится рядом. Источник и SHA-256 полученного файла фиксируются
при подключении. Страница сохраняет `lang="ru"`; runtime-запросов к сервису
шрифтов нет. Генерированный растр не заменяет файл шрифта.

Объявления `@font-face` принадлежат `src/fonts.css` и импортируются из
`src/styles.css`: Vite включает их в общий CSS приложения. Отдельный
блокирующий stylesheet шрифта в HTML не добавляется. WOFF2, лицензия и
проверенные хеши источника остаются в `public/fonts/commissioner`.

| Роль                       | Размер / line-height                                | Вес |
| -------------------------- | --------------------------------------------------- | --- |
| Основной заголовок desktop | 36 / 44 px                                          | 650 |
| Основной заголовок mobile  | 32 / 40 px                                          | 650 |
| Заголовок секции           | 24 / 32 px                                          | 650 |
| Подзаголовок               | 20 / 28 px                                          | 650 |
| Основной текст, ввод       | 18 / 28 px                                          | 400 |
| Кнопки                     | 18 / 28 px                                          | 500 |
| Подписи полей              | 16 / 24 px                                          | 500 |
| Помощь, ошибки, пояснения  | 16 / 24 px                                          | 400 |
| Итог в уведомлении успеха  | 24 / 32 px desktop, 20 / 28 px mobile               | 500 |
| Бренд                      | По компоновке, не меньше основного заголовка mobile | 700 |

Видимый пользовательский текст не уменьшается ниже 16 px для размещения.
Количество билетов и сумма в уведомлении успеха имеют одинаковый вес 500;
вложенный `strong` наследует его и не усиливает жирность автоматически.
Капительные микроподписи и искусственно разреженный трекинг не применяются.
Обычная длина поясняющего текста — до 65 символов на строку. Длинные имена,
email, номера заказов и сообщения переносятся без горизонтального overflow.

### Редакционные правила

Принято пользователем 23 октября 2026 года. Правила относятся к русскому
UI Sqoch на всех ширинах, включая доступные имена и описания.

- Заголовки, подписи полей, кнопки, короткие пояснения, тултипы, статусы,
  одиночные ошибки и сообщения успеха пишутся без конечной точки:
  «Все поля обязательны», «Один адрес на всех участников», «Укажите имя».
- В компактной подписи из нескольких предложений точки между предложениями
  сохраняются, последняя точка опускается. Если требуется развёрнутое
  объяснение, оформить его обычным абзацем с полноценной пунктуацией.
- В содержательных инструкциях и alert-описаниях из двух и более предложений
  сохраняется обычная пунктуация. Это относится к правилам покупки и сообщениям
  о неизвестном результате подтверждения: причина и восстановление должны
  оставаться различимы. Нельзя удалить всю пунктуацию регулярным выражением.
- Сохраняются `?` по смыслу, многоточие ожидания `…`, точки в адресах,
  сокращениях, числах, технических идентификаторах и принятом бренде `sqoch.`.
  Кавычки — «ёлочки»; возрастные диапазоны — 14–17, денежные суммы используют
  неразрывный пробел перед ₽. Правила не зависят от переноса строки на mobile.
- В подсказках, правилах покупки и ошибках роль взрослого называется
  «сопровождающий от 18 лет». «Участник» остаётся общим названием человека
  в заказе; оно не подменяет название роли сопровождающего. Названия полей
  и machine-readable ключи API ради редакционного правила не меняются.
- Краткость не должна скрывать смысл. Ошибка называет незавершённое действие,
  понятную причину и следующий шаг с названием доступной кнопки. Подсказка
  объясняет формат или ограничение, а не требует знания внутренних терминов.
  Для имени, возраста и email локальная и серверная валидация используют
  одинаковые формулировки. Развёрнутые сообщения сохраняют обычную пунктуацию.
- В booking «Данные остались на этой странице» означает только текущий черновик в памяти.
  Нельзя обещать сохранение после обновления страницы, отправку писем или
  реальное бронирование. Неизвестный результат подтверждения отличают от
  доказанного отказа и прямо называют возможность, что сервер создал заказ.

Принцип коротких подписей согласуется с русскоязычными
[Контур.Гайдами](https://guides.kontur.ru/principles/text/styleguide/).
Подобные правила ранее применены в Seller Platform и ARTGROUP; в Sqoch
принято собственное правило, без зависимости от их checkout и без переноса
частных предпочтений других проектов.

## Пространственный ритм и адаптивность

Базовая шкала: 4, 8, 12, 16, 24, 28, 32, 40, 48, 56, 72 px.
Отступы разделяют смысловые группы; подпись и её поле остаются рядом.
Сначала применяются пространство, выравнивание и типографика, затем лёгкий
разделитель. Каждой строке или секции отдельная карточка не нужна.

| Отношение                      | Desktop  | Mobile                             |
| ------------------------------ | -------- | ---------------------------------- |
| Внутренний отступ группы       | 24–32 px | Горизонтальные поля страницы 24 px |
| Между логическими группами     | 32–40 px | 24–32 px                           |
| Между секциями                 | 48 px    | 32–40 px                           |
| Заголовок группы → содержимое  | 24 px    | 16–24 px                           |
| Подпись → поле                 | 12 px    | 12 px                              |
| Между связанными полями        | 28 px    | 16 px                              |
| Поле → помощь/ошибка           | 8–12 px  | 8–12 px                            |
| Содержимое → основное действие | 32 px    | 32 px                              |

На desktop рабочая область занимает примерно 720–760 px. Разделы имеют
узкую левую колонку названий около 128 px, промежуток 32 px и правую колонку
содержимого до 520 px. Это единый формуляр, а не две независимые колонки
контента. Заголовок страницы и краткое вступление выровнены с содержимым
правой колонки. Названия «Билеты», «Участники» и «Email» помогают
читать разделы; отдельные карточки на каждую строку не нужны.

Имя занимает около 360 px, возраст — 112–128 px. Email — около 400–440 px.
Поля ограничены доступной шириной колонки. Desktop-кнопки имеют ширину по
содержимому с внутренними отступами и ориентиром минимальной ширины 240 px,
ограниченной доступным местом; не растягиваются на всю рабочую область.
Основные действия находятся под соответствующим содержимым. На проверке и
результате сохраняются разделы «Участники» и «Email» с той же левой колонкой;
редактирование относится к своему участнику или адресу. Демопереключатель
находится в области проверки перед подтверждением и остаётся доступным при
`sold_out` для прямого ручного повтора.

Ниже 720 px названия разделов переходят над содержимым; горизонтальные поля
страницы — 24 px. Имя занимает отдельную полную строку, возраст — следующую
короткую строку. В мобильной сводке заголовок «Участники» не повторяется;
участники следуют сразу за названием мероприятия. Действие изменения email
находится рядом с его подписью, адрес занимает следующую полную строку.
Между связанными записями используются внутренние отступы 16 px, между
сводкой, демосценарием и действием — 24 px. Основные действия могут занимать
доступную ширину; кнопки и
поля сохраняют доступные размеры. На 360×800 первые поля видны в начальном
viewport; верх страницы не расходуется на декоративный hero или длинное
вступление. Компактные название мероприятия из API и тарифы находятся перед
полями. Тарифный вводный блок не повторяется на проверке и результате.
Возрастные границы и правило сопровождения остаются понятны из тарифов и
контекстных подсказок; декоративный постер не используется.

Проверяются также 768 px, увеличение 200% и длинные значения. Компактность
достигается иерархией, устранением повторов и отступами из шкалы, сохраняя
размеры текста, полей, кнопок и областей нажатия.

### Стабильность строк и обратной связи

Строка заголовка участника резервирует 44 px независимо от наличия удаления.
Появление кнопки «Удалить» при добавлении второго участника не сдвигает поля
уже существующей строки. У каждого участника постоянно предусмотрено не
менее 48 px под тарифную помощь/статус — место для двух коротких строк.
Обычная смена тарифной подсказки не меняет высоту строки. Длинная ошибка
переносится и расширяет область по содержимому; текст не обрезается и не
скрывается ради фиксированной высоты.

Общая подсказка о сопровождении занимает постоянную зону состояния состава
рядом с добавлением и имеет одинаковый текст при любом введённом возрасте.
Она не появляется и не исчезает при вводе каждой цифры и не меняет название
или положение действия «Добавить участника». Название этого действия постоянно
и не заменяется на «Добавить взрослого» в зависимости от возраста.
Новый участник добавляется после существующих строк; элементы ниже естественно
сдвигаются вниз без перестройки уже заполненных строк и без анимации высоты.

Начальная загрузка и ошибка мероприятия используют область не ниже `100svh`.
Футер не появляется на месте будущей формы в первом viewport и не исчезает
из него после ответа API. Это минимальная высота только начального состояния;
она не фиксирует высоту формы, сводки или длинных сообщений.

В режиме `forced-colors` интерфейс принимает системную палитру. Маски иконок
сохраняют видимый силуэт через `CanvasText`, внутри кнопок — `ButtonText`,
в disabled-кнопке — `GrayText`. `forced-color-adjust: none` применяется
только к маске иконки; страницы, текст и контролы не исключаются из адаптации.

## Компоненты и состояния

Повторяемые кнопки, поля, уведомления и индикатор шагов имеют небольших
локальных владельцев. Форма участников и сводка остаются в модуле
бронирования. Новый UI framework, Storybook и отдельный пакет компонентов
не требуются. Второй этап добавляет отдельные маршруты кабинета по дополнению ниже.

| Компонент                   | Требования и состояния                                                                                                                                                                                                                                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Кнопка                      | Primary, secondary и текстовое опасное действие; default, hover, focus, active, disabled, loading. Высота от 56 px; текст при переносе не обрезается. Loading называет выполняемое действие и блокирует повтор.                                                                                          |
| Текстовое действие / ссылка | Название описывает результат. Область нажатия от 44×44 px; ссылка различима без одного лишь цвета. Стрелки и шевроны в шаблонах действий отсутствуют.                                                                                                                                                    |
| Поле                        | Видимая подпись, помощь и связанная ошибка; default, hover, focus, filled, disabled, error. Высота от 56 px. Ошибка сохраняет доступное имя и `aria-describedby`; placeholder не заменяет подпись.                                                                                                       |
| Помощь у подписи поля       | Иконка info с именованной кнопкой 44×44 px. Дополнительная помощь открывается hover, клавиатурным фокусом или нажатием; закрывается Escape, повторным нажатием и нажатием снаружи. Переход указателя на подсказку не закрывает её. Текст связан с полем и кнопкой; ошибка остаётся видимой у поля.       |
| Участник                    | Легенда, имя, возраст, удаление при количестве больше одного. Строки разделяются пространством/линией. Тариф поясняется по введённому возрасту, общее правило сопровождения показано постоянно. Лимит 4 объясняется рядом с добавлением. Для заполненной удалённой строки доступна одноуровневая отмена. |
| Шаги                        | Компактный индикатор двух этапов: данные и проверка. Результат отображается отдельным статусом. Текущий этап назван семантически, предыдущий различим без одного цвета. Порядок не кодируется стрелками.                                                                                                 |
| Демопереключатель           | Одна компактная постоянно открытая радиогруппа с видимой легендой и вариантами успех/нет мест. Доступен с клавиатуры, заблокирован во время запроса; влияет только на confirm. На одном экране не дублируется.                                                                                           |
| Уведомление                 | Информация, ошибка, предупреждение, успех и ожидание. Понятный заголовок/текст, нужное действие восстановления; цвет дополнителен. Alert/status выбираются по смыслу, сообщения не дублируются многократно.                                                                                              |
| Сводка                      | Участники, типы/цены, email и итог из сервера. Длинные значения переносятся, сумма различима. Участник и email имеют адресное редактирование с фокусом на выбранном поле; черновик сохраняется, прежний расчёт отменяется. При `sold_out` сводка остаётся видимой и доступен прямой ручной повтор.       |

Фокус — видимое кольцо 3 px с отступом 3 px, отдельное от selected state.
Не скрывать клавиатурный фокус. Переходы — 120/180 мс; при
`prefers-reduced-motion: reduce` отключаются без потери смысла.
Градиенты, glass, тяжёлые тени, декоративные стрелки и вложенные карточки
не применяются.

## Поведение и пользовательский текст

- Бренд не сбрасывает черновик. Начало нового заказа — отдельное явное действие.
- Удаление заполненного участника допускает одноуровневую отмену с актуальными
  значениями и исходной позицией. Удаление/отмена управляют фокусом и не
  разрешают выйти за пределы 1–4. Отмена — короткое локальное сообщение
  с одним действием на месте удалённой строки, без поиска в конце длинной
  формы. Видимая команда «Вернуть» входит в доступное имя кнопки.
- Обязательность всех полей сообщается до формы и через нативный `required`.
  Собственная валидация и доступные ошибки сохраняются (`noValidate`).
- Тарифная подсказка соответствует введённому возрасту; пустой возраст не
  получает тариф. Дополнительная помощь о полных годах и возрасте до года находится
  у иконки рядом с подписью возраста, а не в отдельной строке под полем.
  Текущая формулировка: «Укажите число полных лет. Если ребёнку ещё нет года,
  введите 0».
  Она остаётся доступным описанием пустого поля через `aria-describedby`;
  допустимое значение получает описание тарифа, ошибка — конкретное сообщение.
  Тариф сохраняется под полем на desktop справа, на mobile слева. Резерв 48 px
  остаётся и при пустом возрасте, сохраняя положение соседних элементов.
  Подсказка выводится над подписью, без перекрытия ввода возраста и изменения
  высоты формы. На desktop она
  выравнивается по правому краю строки подписи, ниже 720 px — по левому,
  чтобы не выходить за viewport. Иконка имеет реальную область 44×44 px;
  вертикальный margin компенсирует её размер в строке подписи 24 px, не
  уменьшая область нажатия. Нативная подпись и ширина input сохраняются.
  Hover/focus-поведение проверяется по
  [WCAG 1.4.13](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html).
  Доступное описание добавления сообщает лимит ещё до его достижения;
  при четырёх участниках пояснение также видно рядом с кнопкой.
  Если ребёнку младше 14 лет не хватает сопровождающего,
  постоянная зона состояния объясняет требование сопровождающего от 18 лет в этом
  заказе. При наличии места используется то же действие «Добавить участника»:
  оно добавляет пустую строку и переводит фокус на имя; возраст 18 и имя не
  подставляются. Один сопровождающий достаточен для всех детей в заказе;
  правило не требует соответствия один к одному. Достигнутый лимит не обходится.
- После удаления, групповой ошибки, серверной 422 и повторной загрузки фокус
  получает подходящее поле, группу или заголовок. Исходная загрузка не вызывает
  неожиданного прокручивания. Повторный отказ загрузки возвращает фокус на
  действие повтора с доступным описанием ошибки.
- Ожидание различимо. Таймаут запросов — 15 секунд; сеть, таймаут и отсутствие
  мест не смешиваются. Повтор подтверждения только ручной. При потере ответа
  нельзя утверждать, что заказ точно не создан. Это относится также к
  повреждённому или некорректному ответу подтверждения и ошибке сервера.
  Общая ошибка запроса находится непосредственно перед кнопкой его ручного
  повтора: интервал 24 px на форме и 24/32 px на проверке. После ошибки фокус
  получает сообщение с мгновенной прокруткой к середине viewport, чтобы
  сообщение и действие восстановления были видны вместе. Следующий Tab
  ведёт к повтору. Полевые и групповые 422 остаются у соответствующих данных.
  Между ошибкой загрузки мероприятия и повтором используется один отступ
  32 px, без сложения двух margin.
- Редактирование конкретного участника или email возвращает сохранённую
  форму, отменяет расчёт и ставит фокус на выбранное поле. После изменения
  нужен новый серверный расчёт.
- При `sold_out` видны сохранённые серверные состав и сумма, выбранный
  демосценарий и прямое действие ручного повтора подтверждения. Промежуточный
  возврат на отдельную проверку для неизменённых данных не требуется.
  У кнопки подтверждения обязательно видно error-уведомление с причиной
  отказа, отсутствием созданного заказа, пределом сохранения данных и
  инструкцией выбора «Успех» и ручного повтора. Оно имеет `role="alert"`,
  получает фокус и прокручивается в viewport вместе с кнопкой. Один заголовок
  страницы не заменяет уведомление рядом с действием. Повтор того же сообщения
  над сводкой не нужен. Отказ остаётся видимым при смене radio и исчезает при
  новой попытке, редактировании или успешном результате.
  Демогруппа объясняет, что выбор сработает только после нажатия кнопки.
  Её описание при смене radio остаётся одинаковым, поэтому кнопка не смещается.
  Длинная подсказка свободно переносится; резерв 48 px — минимум, не ограничение
  высоты. Выбор radio сам не отправляет запрос и не создаёт заказ.
- Успех сначала показывает количество билетов и сумму из ответа confirm,
  затем полный идентификатор заказа. Идентификатор доступен для чтения и
  переноса, но не вытесняет результат и следующее действие.
- Тексты поясняют email примером, используют «младше 14 лет» и корректное
  склонение возраста. Не обещают оплаты, писем, реальных остатков или других
  отсутствующих возможностей. Один факт сообщается один раз в нужном
  контексте; краткие подписи заменяют повторяющиеся инструкции.

## Кабинет организатора: дополнение второго этапа

Статус: реализовано; результаты SQOCH-28 и итогового ревью SQOCH-29 — в
[приёмке](acceptance.md). Основание — [требования уведомлений](notifications.md).
Тот же «Формуляр с разделами»,
Commissioner, токены, размеры и правила текста; новое визуальное направление
не вводится. Правила сохранности/почты в разделах booking выше остаются его
правилами; кабинет показывает сохранённые данные и локальную доставку Mailpit.

Поверхности: список рассылок, редактируемый черновик, предпросмотр,
подтверждённая рассылка с прогрессом. Компактная навигация «Билеты» / «Рассылки»
не сбрасывает сохранённую рассылку; уход из несохранённого draft предупреждается.
Полноэкранный чат, сайдбар с чатами, декоративный dashboard и карточки KPI
не нужны. Рабочая ширина остаётся 720–760 px с колонкой названий разделов.

Форма состоит из разделов «Помощник», «Мероприятие», «Уведомление»,
«Получатели». У помощника textarea запроса и действие «Подготовить уведомление»;
для правки текста — короткая инструкция и «Изменить текст». Ниже обычные
select мероприятия, дата с годом, время, подпись `Europe/Moscow (UTC+3)`,
тема и textarea письма. Предложенная AI дата — отдельная подсказка; год/дату/
время организатор явно вводит в поля, без автоматической подстановки из LLM.
Plain-text предпросмотр не рендерит HTML модели.
Тема/текст редактируются без открывания отдельных диалогов.
В начале есть объяснение двух способов подготовки и «Заполнить вручную»:
действие переводит фокус на выбор мероприятия, не вызывая модель. Список
рассылок различает записи темой, мероприятием и новой датой; у подтверждённых
виден общий результат отправки. Заголовок вкладки соответствует текущему экрану.

Список получателей полностью доступен, без ручных checkbox адресатов.
На desktop — компактные строки email/статус/попытки; на mobile эти значения
складываются в один блок записи, без горизонтального scroll и уменьшения
шрифта. Причины ошибок переносятся. Статус передаётся текстом, не только цветом.

Внизу формы видны состояние сохранения, «Сохранить черновик» и
«Проверить рассылку». Перед проверкой обязательна отметка «Текст соответствует
мероприятию и новой дате». Любое изменение формы её снимает; внешнее изменение
события требует новой проверки по актуальной версии. Оба AI-действия сначала
сохраняют текущие поля; ошибка сохранения не запускает модель. Предпросмотр
показывает прежнюю/новую дату и полный список; единственное основное действие —
«Подтвердить перенос и отправку». Кнопка объясняет оба эффекта, а не прячет
изменение даты за словом «Отправить». Изменённый список требует нового
предпросмотра, прежний клик не переносится на него автоматически.

Во время AI-генерации форма заблокирована, видна выполняемая операция;
ожидание, ответ и ошибка находятся у вызвавшего их действия. После подготовки
фокус переходит к необходимому полю (дата/мероприятие), после правки — к тексту;
фокус в навигации не перехватывается. Конфликт версии показывает «Обновить
сведения» в том же сообщении; обновление сохраняет введённые правки.
После ошибки прежние поля остаются. Уход отменяет ожидание текущего экрана,
но сервер может сохранить ответ: при возврате загружается актуальная версия.
Общий AI deadline — 60 секунд;
обычные API-запросы сохраняют 15 секунд. Ошибка подтверждения ведёт к
проверке состояния той же рассылки, а не к автоматическому новому заказу.
Успех означает принятие локальным Mailpit: «Открыть письма в Mailpit» ведёт в
его UI. «Проверить результат отправки» выполняет серверную сверку без отправки
писем; это отдельное действие. Если неопределённость осталась, сообщение
называет её явно, не ограничиваясь словами «Сверка завершена».

На странице результата после мероприятия и дат идут «Отправлено X из Y»,
отдельные количества ожидающих, ошибок и требующих проверки и доступные
«Продолжить отправку» / «Проверить результат отправки». Затем идут построчные
результаты и полный неизменяемый текст. Длинное письмо не отодвигает прогресс
и восстановление. Подробная справка о повторах, лимите и неопределённости
доступна через нативный раскрываемый блок: смысл и текст не сокращаются ради
компактности. В предпросмотре письмо по-прежнему полностью видно до подтверждения;
рядом с кнопкой объясняется, что подтверждённую рассылку нельзя изменить/отменить.
Failed с лимитом показывает «Не отправлено: исчерпан лимит попыток»;
unknown — «Требует проверки». Нет кнопки принудительной переотправки.
При ошибке получения прогресса последние данные остаются с пометкой
«Не удалось обновить статус», отсутствие ответа не превращается в успех.

Polling не перехватывает фокус и не озвучивает всю таблицу каждые две секунды;
изменившийся общий статус объявляется через одну polite live region.
Ошибка ручного действия получает фокус рядом с восстановлением. Поля имеют
label, ошибки связаны через aria-describedby. Проверяются клавиатура,
desktop 1440×1050, 360×800, 768 px, 200%, forced colors и reduced motion.
Снимки нового кабинета не подменяют существующие evidence booking.

## Приёмка и предел доказательства первого этапа

Новая система применяется к загрузке/ошибке мероприятия и повтору; пустой и
заполненной форме с 1/4 участниками; локальным/серверным полевым и групповым
ошибкам; ожиданию quote; проверке/редактированию; ожиданию confirm;
сети/таймауту; успеху, `sold_out` и новому заказу.

Приёмка включает реальные desktop 1440×1050, mobile 360×800 и промежуточные
768 px, клавиатуру, 200% zoom, reduced motion, размеры текста/контролов,
контраст и отсутствие горизонтального overflow. Все основные экраны и
характерные ошибки/ожидание сохраняются отдельными реальными скриншотами.
Визуальное сравнение с выбранным «Формуляром с разделами» проверяет композицию,
иерархию и характер компонентов; размеры и адаптивность — по этому документу.
Отдельно проверяются добавление второго/четвёртого участника, смена возраста
между пустым/13/14/18, постоянство подсказки сопровождения и длинные ошибки:
существующие поля не сдвигаются из-за краткого статуса или появления удаления.

После внедрения проводится сценарный проход по
[эвристикам Нильсена](https://www.nngroup.com/articles/ten-usability-heuristics/):
сценарий → эвристика → наблюдение → исправление → повторная проверка.
Поведенческие исправления сопровождаются содержательными red/green,
оформление — браузерными и визуальными свидетельствами. Проверка документа
и растрового изображения не подтверждает CSS, браузерную доступность или
реальную связку UI/API. Новые свидетельства не перезаписывают исторические.

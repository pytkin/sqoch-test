# SQOCH-39–44: мероприятия и подготовка переноса

План принят пользователем 27.10.2026. Функциональные правила принадлежат
[требованиям](notifications.md), архитектура [техническим решениям](notifications-technical.md),
DTO и revisions [контракту](notifications-contract.md). Этот журнал владеет
порядком срезов, критериями и их текущим статусом; фактические результаты
проверок и ограничения находятся в [приёмке](acceptance.md).

## Цель и границы

Кабинет открывает мероприятия и текущие даты. Поток: мероприятие → помощник
либо ручной ввод → необходимое уточнение → проверка подготовленного переноса
→ отдельное подтверждение → результат уведомления и история события.

Сохраняются SQLite/campaign UUID, старые ссылки, snapshots, доставки и принятый
минеральный kit. Содержательный ввод сохраняется до LLM, пустое посещение не
создаёт запись. Полная дата из запроса заполняется без повторного ввода;
без года применяется принятая ниже политика current_year, остальные
недостающие компоненты и относительные выражения уточняются. Человеческая
отметка проверки текста обязательна. Дата события меняется только confirm.
Полноценный чат, CRUD мероприятий, новая визуальная система и внешняя доставка
не добавляются.

Документальный шаг SQOCH-39 не является поведенческим RED. Для каждого
поведенческого среза нужны отдельные исполняемые положительный и отрицательный
случаи с содержательным RED, затем минимальный green и рефакторинг. Ошибки
импорта/установки не являются RED приложения. Более ранние сильные проверки
не заменяются только новым happy path.

После каждого среза требуется новый независимый рецензент с чистым контекстом.
Подтверждённые P0–P2 исправляются и повторно проверяются до зависимого
продолжения. Каждый контрактный срез обновляет Pydantic, генерацию TS,
guards/consumer и fixtures вместе; `contracts:check` обязан оставаться green.

## Уточнение года от 27.10.2026

Во время реализации пользователь принял вариант «Текущий год; уточнять при
прошедшей дате или противоречии с годом мероприятия». Он заменяет прежний
always-ask при отсутствии года. Явный год имеет приоритет. Current_year берётся
из injected server Clock в Europe/Moscow только при совпадении с московским
годом мероприятия и строго будущем календарно корректном результате. В других
случаях спрашивается year; следующий год не выбирается и год события не
наследуется. Полный год и источник видимы, сохранённый год не пересчитывается
на GET/reload. Прошедшая после смены года дата требует явного исправления
либо новой подготовки.

Optional nullable поле `year_source:explicit|current_year|clarification|manual`
добавлено в SQOCH-41. V1 JSON без поля получает null; SQL-колонка 002 не меняется.
Отдельные RED-сценарии SQOCH-41 прошли green и независимое ревью:

- Clock 2026-10 Moscow, событие 2026-11, запрос «2 декабря, 19:00»:
  applied с 2026 и current_year, без вопроса о годе.
- Целевая дата уже прошла в текущем году: targeted year clarification,
  без автоматического перехода на 2027.
- Clock 2026 и мероприятие 2027: targeted year conflict, без наследования 2027.
- Явный 2027 в запросе имеет приоритет перед current_year.
- Clock на границе UTC/Moscow 1 января использует московский календарный год.
- GET/reload сохраняет однажды выбранный год; после year rollover не сдвигает
  его, прошедшая дата блокируется до явной коррекции/новой подготовки.

Закрытый SQOCH-39 проверял прежнюю политику уточнения. Новая политика отдельно
прошла focused review перед реализацией SQOCH-41, затем независимое ревью
завершённого среза. Эти результаты сохранены в журнале ниже.

## Переход без потери данных

- Перед изменением рабочей схемы остановить только её проектные API/worker,
  сделать согласованную SQLite-копию, применить upgrade и запустить их снова.
  Live shared lock запрещает миграцию при работающем прежнем процессе.
- Не использовать demo reset/load для перехода. Сохранить старые UUID,
  revisions, previews/tokens, snapshots, MIME, Message-ID и состояния доставки.
  `suggested_start` не повышается автоматически до новой даты переноса.
- Не удалять старые пустые или unassigned записи. Основной обзор их фильтрует
  по содержательности, прямые ссылки действуют, значимые unassigned доступны
  для продолжения. Несколько подготовок события остаются отдельными.
- Не перезаписывать чужой накопленный diff. Копия/состав дельты и подходящие
  проверки фиксируются перед каждым изменением, не выполняется reset/clean.

## Итоговые gates

1. `pnpm verify`: обе волны, генерация типов, lint/typecheck/format/docs,
   backend и frontend, desktop/mobile E2E.
2. `pnpm test:mutation`: сохранить 33 существующих предметных мутации,
   обновить anchors при рефакторинге и добавить проверки resolver, изоляции
   истории, человеческой отметки и отсутствия создания при чтении. Invalid,
   timeout и отсутствующий anchor не считаются killed.
3. Свежие desktop/mobile снимки новых состояний, keyboard/focus, reflow на
   узких ширинах, длинные значения/ошибки, contrast и принятые токены.
4. Настоящий DeepSeek: достаточный запрос заполняется автоматически,
   допустимый current_year не вызывает лишний вопрос; оставшаяся неполнота
   возвращает конкретное уточнение. Сохранённые ответы и год переживают reload.
5. Отдельные SQLite и Mailpit project `sqoch-mailpit-tests`, 11025/18025:
   до confirm событие/доставки неизменны, после confirm все 8 To/subject/body
   совпадают с проверенным текстом, каждый Message-ID встречается один раз.
   Повторить `pnpm test:mailpit` для настоящих 451/crash/restart/unknown.

Свежая интеграционная приёмка дополняет SQOCH-38, который проверял прежний
путь с повторным ручным вводом даты. Старое evidence не объявляется проверкой
нового автозаполнения. `.env` и ключи не попадают в свидетельства. Основной
Mailpit volume сохраняется. Видео, push и публикация требуют отдельного
указания; запись процесса не ведётся.

SQOCH-40 завершён после нового независимого ревью: 345 backend tests,

протоколом провайдера, ограниченным HTTP-чтением, deadline и освобождением клиента.

## Маршруты и обзор мероприятий

Общая шапка содержит «Билеты / Мероприятия»; шаг booking находится внутри
оформления. Hash-router не получает новую зависимость:

| Маршрут                                | Экран                                                  |
| -------------------------------------- | ------------------------------------------------------ |
| `#/booking`                            | Билеты; `/` остаётся его совместимым входом            |
| `#/organizer`                          | Обзор мероприятий с текущими датами и состоянием работ |
| `#/organizer/events/:eventId`          | Мероприятие, подготовки и история переносов            |
| `#/organizer/transfer`                 | Помощник без выбранного события                        |
| `#/organizer/events/:eventId/transfer` | Помощник в контексте события                           |
| `#/organizer/campaigns/:campaignId`    | Сохранённая подготовка или результат по прежнему UUID  |

Обзор и история группируют существующие чтения events/campaigns по event_id;
отдельный CRUD или сервис истории не нужен. Неизвестный organizer-маршрут
показывает понятный отказ, не подменяется booking. Подтверждённая история
использует event_snapshot, текущая дата события показана отдельно. Общий
обзор не показывает пустые legacy-записи; прежние прямые ссылки действуют.
Значимые подготовки без события находятся в «Продолжить подготовку».
Несколько подготовок одного события не объединяются автоматически.

Существующий `OrganizerEvent` остаётся формой вложенного события старых
preview: новые required поля в него не добавляются. Данные истории и
содержательности добавляются в CampaignSummary, а не в сохранённый Event DTO.

## SQLite, миграции и жизненный цикл

Файл по умолчанию — `data/sqoch.sqlite3`, вне Git вместе с WAL/SHM и lock-файлом.
`SQOCH_DATABASE_PATH` задаёт явный путь; тесты используют временный каталог.
Путь канонизируется до открытия БД и lock-файлов; альтернативные hardlink
и сетевые пути не поддерживаются. Файлы блокировок не удаляются при reset.
Локальная файловая система; не сетевой диск. Включены foreign keys, WAL,
`synchronous=FULL`, busy timeout 5 секунд. Соединение принадлежит операции,
не разделяется между потоками. Изменение состояния — короткая явная транзакция;
LLM/SMTP/HTTP не выполняются внутри транзакции.

Нумерованные SQL-миграции применяются по одному разу с журналом версий.
Миграция и запись её версии атомарны; более новая неизвестная схема — ошибка
запуска, не молчаливое пересоздание БД. Обычный старт создаёт/обновляет схему,
но не загружает fixtures и не сбрасывает данные.

| Таблица             | Минимальные данные и ограничения                                                                                                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `events`            | id, title, starts_at_utc, timezone, revision; стабильный ID, timezone Europe/Moscow                                                                                                                                   |
| `purchases`         | id, event_id FK, email, normalized_email, status active/cancelled; индекс event/status                                                                                                                                |
| `campaigns`         | UUID id, draft revision, выбранные event/new date, subject/body, text_reviewed, исходная просьба, nullable assistant_state_json, preview token/snapshot, confirmed_at, old/new event snapshots; draft/confirmed phase |
| `deliveries`        | id, campaign_id FK, normalized_email, state, attempts 0..5, next_attempt_at, message_id, неизменяемое MIME, last_error_code, sent_at, mailpit_message_id                                                              |
| `schema_migrations` | номер применённой миграции                                                                                                                                                                                            |

`UNIQUE(campaign_id, email)` (delivery.email уже нормализован серверной выборкой),
уникальный `message_id`, CHECK
состояния и счётчика дополняют проверки приложения. Снимок event содержит
название, прежнюю/новую дату и timezone, чтобы история не менялась при
следующем переносе. Счётчики прогресса вычисляются из deliveries, не ведутся
второй независимо изменяемой копией.

Команды БД реализованы в SQOCH-22; dev-запуск worker — в SQOCH-24. Нормативное поведение:

- `pnpm db:init`: идемпотентно применить миграции, ничего не удалить.
- `pnpm demo:load`: целиком проверить Pydantic-схемой JSON, затем атомарно
  upsert событий/покупок по ID; не удалять отсутствующие ID и не менять
  campaigns/deliveries. Изменение event увеличивает revision. Команда может
  вернуть дату из fixtures: это явная операция загрузки, не часть старта.
  Ровно 20 покупок гарантирует чистая загрузка; произвольные ручные добавления
  не удаляются неявно.
- `pnpm demo:reset`: только при остановленных API/worker и явном `--yes`
  пересоздать тестовую БД и загрузить fixtures. API и worker держат shared
  maintenance-lock весь срок жизни; reset получает exclusive nonblocking
  lock до первого удаления, иначе отказывает. Отдельно предупреждает о
  потере рассылок; Mailpit volume не очищает. ID новых рассылок всегда новые.
- `pnpm dev`: привычный запуск web/API плюс worker; Ctrl+C завершает все три.
  Production-style локальный просмотр dist получает отдельную инструкцию
  запуска API и worker. Один API-процесс, один worker на файл БД.

Файл fixtures в Git; секреты, SQLite и пользовательские письма в Git не входят.
Сохранённая подготовка может содержать неполные поля; строгая полнота нужна
на preview/confirm. Открытие страниц и переключение режима ничего не создают.
Первый содержательный PUT атомарно сохраняет запрос либо ручные данные с
клиентским UUID. Повтор этого UUID возвращает существующую запись без
перезаписи новым payload. Пустой `{}` остаётся совместимым API-входом, но
новый UI его не использует. Автоматически выбранный контекст страницы сам
по себе не является содержательным пользовательским действием.

Новая миграция 002 добавляет nullable `assistant_state_json` с версионированной
Pydantic-структурой. Она хранит режим assistant/manual, исходный запрос,
структурированные ответы, проверенные частичные компоненты даты, контекст,
происхождение ручных значений, уточнения и стадии intake/applied/needs_input/failed.
Ни chat history, ни raw provider response не сохраняются. Старые UUID, revisions,
MIME, Message-ID, snapshots и принятые tokens не меняются; старые assistant state
нормализуются в null. Legacy `suggested_start` остаётся читаемым и никогда
автоматически не переносится в `proposed_start`.

Перед upgrade останавливаются только API/worker, использующие эту БД, и
создаётся согласованная SQLite-копия. Миграция с версией выполняется атомарно;
live shared lock запрещает upgrade. Не запускать demo reset/load для перехода:
это может изменить сохранённые даты. Mailpit volume сохраняется. Откат к
копии допустим только до новых содержательных записей/SMTP; после них нельзя
терять уже зафиксированные результаты доставки ради отката схемы.

UI показывает несохранённые запрос, ответы и поля и предупреждает об уходе.
Перед AI сначала сохраняются текущие ручные поля через PATCH; ошибка
сохранения останавливает цепочку до сети. PATCH передаёт `manual_fields`
для реально вручную изменённых event_id/date/time. Пустой список не стирает
прежнюю provenance, а обычное сохранение не превращает AI-значения в ручные.
Legacy PATCH без этих метаданных считает фактически изменённые структурированные
поля ручными. Ручная смена события является явным принятым выбором; изменение
компонента даты инвалидирует противоречащие сохранённые partial components.

PATCH также принимает optional `mode:assistant|manual`; отсутствие сохраняет
текущий режим. Ручное сохранение передаёт mode=manual, включая правку только
subject/body. Сохранение человеческой отметки режим не переключает.
Переключение режима в UI остаётся локальным до явного сохранения либо
содержательного действия и само не вызывает PATCH/PUT.

Prepare выполняется в две короткие write-транзакции. Intake проверяет phase и
expected_revision, сохраняет bounded prompt/answers, ставит mode=assistant,
повышает revision на 1,
снимает text_reviewed/reviewed_event_revision и инвалидирует preview; прежние
готовые event/date/subject/body остаются. Разбор и LLM выполняются без write-lock.
Успешный applied либо needs_input сохраняет результат CAS только к intake-revision
и повышает revision ещё на 1. Провайдерный отказ помечает failed операционным
CAS без дополнительной content revision. Out_of_scope также оставляет intake
и прежние готовые поля, stage=failed и исход prepare out_of_scope. Ошибка
старого вызова не может перезаписать состояние более нового intake.

Assistant state хранит intake_revision и applied_revision, чтобы после ошибки
UI отличал предыдущий результат от результата нового запроса. После ошибки,
unknown или reload клиент читает GET того же UUID и синхронизирует revision.
Незавершённый intake не выдаётся за продолжающийся серверный процесс; повтор
требует явного действия. GET не запускает LLM. Rewrite использует сохранённые
структурированные event/date и меняет только текст.

## Контракт кабинета

Все пути ниже имеют префикс `/api/organizer`. Pydantic запрещает неизвестные
поля, boolean вместо чисел и невозможные состояния. Ответы содержат revision,
серверные даты и стабильные коды; ошибки полей сохраняют формат 422 первого
этапа. Изменение контракта сопровождается генерацией и `contracts:check`.

| Метод и путь                     | Вход / результат                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /events`                    | Существующие ID, названия, текущие даты, timezone, revision; без создания записей                                                                 |
| `GET /campaigns`                 | Подготовки/переносы со статусом, has_content, preparation_stage, updated_at и event_snapshot для группировки по event_id                          |
| `PUT /campaigns/{uuid}`          | Содержательный начальный запрос/ручные поля; 201. Повтор UUID возвращает существующее, 200, без перезаписи. `{}` совместим, но UI его не вызывает |
| `GET /campaigns/{id}`            | Подготовка с assistant_state либо immutable результат, revision, результаты по email, счётчики                                                    |
| `PATCH /campaigns/{id}`          | expected_revision, поля формы, text_reviewed, optional mode/manual_fields; 200 с новой revision; только draft                                     |
| `POST /campaigns/{id}/prepare`   | expected_revision, optional prompt/answers/context_event_id; intake и затем applied/needs_input/out_of_scope с уточнениями                        |
| `POST /campaigns/{id}/rewrite`   | expected_revision, instruction; 200 обновляет только subject/body, снимает text_reviewed                                                          |
| `POST /campaigns/{id}/preview`   | expected_revision; 200: token, revision, event snapshot, old/new date, subject/body, полный список email                                          |
| `POST /campaigns/{id}/confirm`   | preview_token; первый успех 202, повтор того же token 200 с той же campaign; никакого нового ID                                                   |
| `POST /campaigns/{id}/resume`    | 200 с актуальным состоянием; разблокирует только retry_wait, не обнуляет attempts                                                                 |
| `POST /campaigns/{id}/reconcile` | 200: результат read-only сверки unknown, причины оставшихся неопределённых                                                                        |

Мутации требуют JSON и проверяют Origin при его наличии: только локальные
origin приложения; CORS не открывается всем. Это узкая защита локального
кабинета, не реализация авторизации. GET ничего не отправляет и не подтверждает.
Для dev/локального dist разрешены только объявленные origin 127.0.0.1/localhost
с портами приложения (5173/8000). Host allowlist — 127.0.0.1 и localhost,
без произвольных доменов, резолвящихся в loopback. Тестовый `testserver`
допускается только явной тестовой настройкой. API Mailpit вызывается HTTPX
с trust_env=false и follow_redirects=false; host — буквальный 127.0.0.1.
Это закрывает DNS-rebinding/redirect обход локальной границы без авторизации.

Сохранение не требует отдельного HTTP-действия для checkbox: PATCH передаёт
полную актуальную форму и явную отметку пользователя, которая относится ровно
к этой revision. UI снимает отметку при любой последующей правке. Запрос,
меняющий содержательные поля без явного text_reviewed=true, сохраняет false;
AI всегда сохраняет false. Новый preview возможен только для сохранённой
проверенной версии. Отметка включает `reviewed_event_revision`, полученную
клиентом вместе с показанным событием. PATCH с true требует выбранное событие
и совпадение этой revision; сервер не подставляет текущую revision вместо
наблюдаемой клиентом. campaigns сохраняет её рядом с text_reviewed.
Preview сравнивает её заново, даже если preview ещё ни разу не создавался.
Изменение исходного события требует повторного показа данных и проверки
текста; старая отметка даёт `text_review_required`. При false revision = null.

### Resolver даты и граница выбора события

Просьба/инструкция ограничена 4000 символами, тема 1–200 без CR/LF,
plain-text body 1–10000 после trim. Один небольшой pure resolver использует
stdlib `datetime`/`zoneinfo`, без новой зависимости или общего NLP-framework.
Поддерживаются `DD.MM.YYYY`, `YYYY-MM-DD`, «20 ноября 2099 года», `H:MM`/`HH:MM`
и ISO timestamp с явным offset, нормализуемый в Europe/Moscow. Частичные день,
месяц и время сохраняются для адресного ответа year/date/time.

Датированное уточнение пользователя 27.10.2026 заменяет always-ask missing year.
Явный год из даты, структурированного ответа либо ручного поля имеет приоритет
перед подстановкой. Если года нет, после получения проверенного контекста
события resolver берёт текущий год из внедрённого server Clock, преобразованного
в Europe/Moscow. Подстановка разрешена только если московский год мероприятия
совпадает с текущим и построенная календарно корректная дата строго будущая.
Иначе возвращается адресное уточнение year: при прошедшем результате past,
при другом годе мероприятия conflict. Следующий год молча не выбирается,
год мероприятия и ответ модели не являются источниками подстановки.

Источник года хранится в optional nullable `year_source` внутри AssistantState:
explicit/current_year/clarification/manual. Это дополнение SQOCH-41 к JSON,
не изменение DTO SQOCH-40 и не новая SQL-колонка. Старые v1 JSON без поля
читаются с null. Автоматически выбранный год сохраняется вместе с результатом,
не пересчитывается на GET/reload или обычном восстановлении. Если после смены
года дата стала прошлой, требуются явная коррекция либо новая подготовка;
preview/confirm по-прежнему блокируют прошлое. В подготовленном результате
полный год виден; current_year сопровождается понятной пометкой источника.

Время не наследуется молча. Относительные выражения, альтернативы, диапазоны и несколько дат, включая
конструкцию с прежней и новой датами, требуют явного выбора целевой даты.
Неподдержанная/неоднозначная форма вызывает уточнение, а не выбор первого или
последнего совпадения. Проверяются реальный календарь, 24-часовое время,
представимость UTC/Moscow, строго будущее начало и отличие от текущего.

Полный однозначный набор, включая допустимую подстановку текущего года,
заполняет `proposed_start` в проекте автоматически без повторного ручного ввода.
Это ещё не меняет событие и не создаёт deliveries. Произвольный ISO из JSON
модели не подтверждает ни явный год, ни условия current_year. Подтверждённые
resolver факты передаются модели для текста; дату модели не применяют.
`proposed_start` в публичном API сериализуется с московским offset.

LLM выбирает существующее мероприятие через ограниченные tools и прочитанный
контекст. Контекст страницы и ручные значения не меняются молча. При другом
событии или конфликте даты возвращается адресное уточнение с сохранением ввода.
Явно принятый `answers.event_id` либо ручной выбор разрешает сменить контекст.
Последующие уточнения сохраняют уже определённые компоненты; новый полный
запрос заменяет прежний запрос, но не скрыто отменяет ручные значения.
Rewrite по-прежнему не меняет event/date. Семантику свободного текста
проверяет организатор; автоматический семантический сканер не вводится.

Коды: 404 `not_found`; 409 `revision_conflict`, `preview_stale`,
`campaign_immutable`, `confirmation_conflict`, `text_review_required`,
`event_campaign_unsettled`; 422 для полей и `no_recipients`;
502 `ai_invalid_response`/`ai_unavailable`;
503 `ai_not_configured`/`storage_unavailable`; 504 `ai_timeout`.
Ответ needs_input — корректный результат подготовки, не ошибка сервера.
При неизвестном результате мутации клиент GET-проверяет тот же ID; не создаёт
новую рассылку и не запускает автоматическую повторную генерацию.

### Предпросмотр и подтверждение

Preview сохраняет случайный token, draft revision и снимок: version события,
его данные, отсортированный набор покупок выбранного события (ID, email,
status), нормализованный список получателей, тему/текст/новую дату и отметку
проверки. Любая правка draft инвалидирует token. Token хранится в БД, а не
только в памяти API. Изменение покупок, даже с прежним итоговым списком,
обнаруживается при сравнении снимка.

Confirm выполняет `BEGIN IMMEDIATE`, затем:

1. Если эта рассылка уже подтверждена тем же token — вернуть сохранённый
   результат, даже если мероприятие позднее менялось. Другой token — 409.
2. Для draft сверить token/revision/снимок и заново проверить будущую дату,
   проверку текста и ненулевую выборку. Несовпадение — 409 без записи;
   UI предлагает обновить предпросмотр, прежний клик не переносится на новый.
3. Проверить отсутствие другой подтверждённой рассылки этого события с
   pending/sending/retry_wait/unknown; иначе 409 event_campaign_unsettled с
   ID такой рассылки. Это предотвращает отправку старого переноса после
   нового из-за задержанных повторов. Проверка и запись в одной транзакции.
   Завершённая рассылка (все sent/failed) не блокирует следующий перенос;
   даты уже отправленных уведомлений не переписываются.
4. Обновить дату и revision мероприятия, заморозить campaign, создать по
   одному delivery с неизменяемым MIME и Message-ID, commit.

Любая ошибка даёт rollback всего переноса. SMTP начинается только после
commit. Повторный HTTP-запрос не создаёт delivery; конкурентные confirm
сериализованы SQLite. Подтверждение другого черновика по устаревшему событию
требует нового preview. После confirm PATCH/AI запрещены.

## DeepSeek и инструменты

Базовый URL `https://api.deepseek.com`, `POST /chat/completions`,
`DEEPSEEK_MODEL=deepseek-flash`, `thinking: {type: disabled}`, `stream: false`,
`max_tokens: 4096`. `DEEPSEEK_API_KEY` читается только backend из окружения;
не используется Vite-префикс, ключ не возвращается в API/логи. Имена моделей
могут меняться у провайдера: перед живой приёмкой проверить доступность
настроенной модели, без молчаливой подмены.

Для prepare используется небольшой ограниченный цикл tool calls, не агентный
framework. Не более четырёх HTTP-вызовов модели и четырёх исполнений tools
на действие, общий deadline 60 секунд, connect timeout 5 секунд. Используются
AsyncClient и asyncio.timeout вокруг всего действия, включая чтение body:
keep-alive строки провайдера не продлевают бюджет. Ответ ограничен 128 KiB.
Служебный необязательный tool_calls.index допускается как неотрицательный
integer/null и исключается из replay; инструменты и аргументы остаются строгими.
Последний
вызов завершает JSON без tools. На промежуточных шагах model получает только
allowlist функций; аргументы валидируются Pydantic перед исполнением:

- `list_events()` — ID, названия, текущие даты и timezone.
- `get_event_context(event_id)` — те же сведения одного события, revision и
  количество уникальных подходящих получателей; без email, имён и покупок.

Применение ненулевого event_id требует получения контекста именно этого
события через tool. Неоднозначный глобальный выбор допускает needs_input с
event_id=null после list_events без get_event_context, но модельный null не
сбрасывает известный контекст страницы или ручной выбор. При предложении
другого события сохраняются ввод и прежние готовые поля, возвращается
уточнение с валидным candidate_event_id для явного перехода. Неизвестный ID
не применяется. Tools не исполняют SQL модели и не имеют полномочий записи,
подтверждения, SMTP или произвольного HTTP. Текст пользователя и tool data
обрабатываются как данные: просьба обойти подтверждение не расширяет allowlist.

Финальный JSON prepare содержит `status: ready | needs_input | out_of_scope`,
`event_id` и `subject/body`; дату в provider DTO не включать. Resolver и
структурированные пользовательские ответы определяют дату до генерации текста.
Fields_to_complete и стабильные clarifications вычисляет backend, не модель.
Полный набор фактов даёт applied и заполненный проект; неполный needs_input
сохраняет подтверждённые части и требует конкретных ответов. `ready` не
заменяет валидацию backend или отметку организатора.

Out_of_scope, некорректный/обрезанный ответ и превышение лимитов не применяют
новые event/date/subject/body. Сохранённый intake остаётся, stage становится
failed через CAS, review и preview уже сняты. Поэтому весь CampaignDetail не
обещается byte-identical после отказа; прежние готовые поля и доставки
сохраняются. Повторное обращение начинается с GET, не с автоматического retry.

Rewrite — один вызов, текущие структурированные поля, тема/текст и одна
инструкция. Возвращает только subject/body или out_of_scope. Нет истории,
tools записи или разрешения менять event/date. Финальный JSON проходит
Pydantic; valid JSON сам по себе не подтверждает правильность содержания.

Prepare проверяет expected_revision/phase до intake и phase/intake_revision
при финальном CAS; rewrite сохраняет проверку expected_revision/phase до и
после сети. Устаревший результат или ошибка не применяются. UI блокирует второй запрос/редактирование
до завершения. Уход со страницы отменяет ожидание UI, но не гарантирует отмену
сохранения на сервере: результат может стать новой сохранённой версией.
Возврат всегда читает GET, поздний callback не меняет другой экран.
Покупки и список email автоматически не прикладываются к запросу модели;
введённые пользователем просьба, инструкция и текст письма передаются DeepSeek.
Поэтому обещание «ни одного email в модели» для свободного текста не даётся.
Логи содержат ID операции/код/имена tools, но не prompt/body/key/raw response.
HTTP 429/5xx и таймаут не ретраятся автоматически, доступен ручной повтор.
Отсутствующий ключ отключает AI с понятным объяснением, но не booking,
сохранение формы, просмотр и уже подтверждённую отправку.

## Worker, SMTP и защита от дублей

Отдельный worker владеет эксклюзивной неблокирующей OS-блокировкой файла рядом
с БД на весь срок работы (stdlib `fcntl` на macOS/Linux; Windows — через WSL2).
Второй worker завершается с понятной ошибкой до обработки. Lock снимается ОС
при аварии; никаких lease с преждевременным перехватом SMTP-задания нет.
Неподдерживаемая среда не запускает worker без блокировки. API лишь создаёт
задания. Даже при ошибке запуска двух циклов SQL compare-and-set разрешает
захват только ожидающей записи. Worker последовательно обрабатывает по одному
адресу; SMTP timeout 10 секунд, polling ожидающих заданий раз в секунду.

До SMTP атомарно выставляются sending, attempts + 1, постоянный Message-ID и
сохранённый MIME. Соединение SMTP новое на попытку, один envelope recipient.
MIME фиксируется с email.policy.SMTP (CRLF) до сохранения: DATA(bytes) не
меняет тело. Ранее сохранённые письма не переписываются при сверке.
From — `Sqoch <organizer@example.com>`, To — только этот получатель; без CC,
BCC, вложений, HTML и индивидуальной генерации. Тело одно для всей рассылки.
Message-ID вида `<delivery-UUID@sqoch.local>` и `X-Sqoch-Campaign-ID` помогают
сверке, но не считаются SMTP-механизмом дедупликации.

| Состояние  | Переход и действие                                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------- |
| pending    | Worker забирает запись, attempts < 5 → sending                                                                                |
| sending    | SMTP 250 после DATA → sent; доказанный временный отказ → retry_wait; окончательный отказ → failed; неопределённость → unknown |
| retry_wait | По next_attempt_at либо ручному resume → sending, только attempts < 5                                                         |
| failed     | Окончательный 5xx или исчерпание 5 попыток; resume пропускает                                                                 |
| unknown    | Только сверка Mailpit → sent при доказанном совпадении; иначе остаётся unknown                                                |
| sent       | Терминальный успех; SMTP больше не вызывается                                                                                 |

Временные отказы: SMTP 4xx или ошибка соединения до передачи DATA, когда
точно известно, что письмо не принято. Повторы после попыток 1/2/3/4 через
5/15/60/120 секунд соответственно; после пятой — failed. Ручной resume
делает retry_wait доступным сейчас, не увеличивает лимит. Ошибка соединения
после начала DATA без окончательного SMTP-ответа, падение процесса и ошибка
фиксации результата после SMTP — unknown. Неизвестная фаза трактуется
консервативно; классификация проверяется отдельными тестами.
Локальный сбой разбора SMTP-ответа во время DATA (общий SMTPResponseException)
не равен доказанному 5xx от сервера: остаётся unknown. Явный SMTPDataError
или полученный код 4xx/5xx сохраняют классификацию доказанного отказа.
Успешный окончательный 250 после DATA не отменяется ошибкой QUIT/закрытия
соединения. После ошибки записи результата в БД worker прекращает обработку;
он не начинает новую SMTP-попытку из неподтверждённого локального состояния.
После восстановления БД прежний sending сверяется как unknown.

При старте под OS-lock оставшиеся sending переводятся в unknown. Pending и
retry_wait сохраняют очередь/время/счётчики. Worker делает одну сверку unknown
при восстановлении; последующие сверки запускаются явной кнопкой. API-сверки
не расходуют SMTP-лимит и допустимы даже при attempts=5.

Mailpit API ищет по `message-id:…`, затем сверяются точный Message-ID,
получатель, заголовок campaign, тема и декодированное тело. SMTP success
либо одно доказанное совпадение даёт sent. Ноль совпадений, ошибка API,
несовпадение содержимого или несколько совпадений оставляют unknown с причиной.
Поиск должен учитывать пагинацию и не принимать частичный матч за точный.
На проверенной версии Mailpit total относится ко всему ящику; filtered
messages_count и длина страницы относятся к поиску. Не использовать total
как число совпадений Message-ID.
Результат сверки записывается CAS только если запись ещё unknown; поздняя
неудачная сверка никогда не понижает sent. Сравнение тела нормализует только
CRLF/LF после MIME decoding, без trim/изменения значимых символов. Message-ID
сравнивается целиком после снятия угловых скобок, не подстрокой.
Никакого автоматического unknown → pending, ручного «считать неотправленным»
или принудительной повторной отправки нет. Это осознанная потеря автоматического
прогресса ради отсутствия дублей при неопределённости, не exactly-once доставка.

Агрегированный статус: draft; processing при pending/sending/retry_wait;
needs_attention при оставшихся unknown без работы; completed если все sent;
completed_with_errors если работа закончена, unknown нет, есть failed.
Unknown отображаются также во время processing. UI показывает sent / total,
отдельно ожидание, повторы, failed и unknown; сумма всегда равна total.
Закрытие страницы влияет только на polling UI (2 секунды), не на worker.

## Mailpit, сохранность и управляемый сбой

Compose публикует только `127.0.0.1:1025:1025` и `127.0.0.1:8025:8025`.
Именованный volume монтируется в `/data`, `MP_DATABASE=/data/mailpit.db`,
`MP_MAX_MESSAGES=0`; ограничение по возрасту писем не задаётся.
`MP_ENABLE_CHAOS=true`, вероятность по умолчанию 0. SMTP relay/forwarding
не настраиваются. `MP_IGNORE_DUPLICATE_IDS` не используется как основание
гарантии приложения. Конфиг отправителя принимает только loopback SMTP/API
Mailpit; произвольные внешние SMTP-host и URL из запроса не допускаются.

Обычные stop/start/down без `-v` сохраняют письма. Удаление volume, очистка
писем через UI и откат БД находятся вне гарантии восстановления; документация
явно объясняет последствия. При отсутствии письма после такого действия
приложение не выдаёт отрицательный поиск за разрешение отправить ещё раз.

В SQOCH-27 реализован demo-runner `pnpm demo:failure`: на отдельной тестовой БД/экземпляре
Mailpit обработать ровно три адреса, поставить межзадачный барьер, включить
Chaos Sender 451 с вероятностью 100%, разрешить четвёртую SMTP-попытку.
Получить настоящий отказ и остановить demo-worker до автоматического повтора.
Затем выключить Chaos, пока worker остановлен выполнить ручной resume и
только затем запустить обычный worker. До resume/start выдержать время больше
retry deadline: в Mailpit остаётся ровно три письма. Уже отправленные три
письма не появляются повторно. Штатные автоматические повторы проверяются
отдельно без demo-барьера. Барьер — только
инструмент демо/тестов, не новая бизнес-функция; штатный worker использует
описанные автоматические задержки. Runner восстанавливает настройку Chaos
в finally и не очищает рабочую БД/почтовый volume.

Отдельная fault-injection точка прерывает worker после успешного SMTP и до
commit sent. После старта сверка должна найти одно письмо и завершить запись
без второго SMTP. Никакой fault-injection не включён обычным запуском.

## Проверки и источники технического выбора

Обычный verify не зависит от ключа, сети DeepSeek и живой почты: использует
временные БД, управляемые часы и transport doubles. Для окончательной приёмки
добавляются `pnpm test:mailpit` с реальным Compose и отдельный ручной/скриптовый
smoke DeepSeek с ключом. Один только mock не доказывает работоспособность
интеграции. Тестовые БД и Mailpit volume отделены от пользовательских.

Проверено по официальным источникам 26.10.2026:

- [DeepSeek: модели](https://api-docs.deepseek.com/quick_start/pricing/):
  актуальное имя `deepseek-flash`, поддержка tool calls и JSON.
- [DeepSeek: tool calls](https://api-docs.deepseek.com/guides/tool_calls/)
  и [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/):
  нестриминговые вызовы, thinking disabled, исполнение tools приложением.
- [DeepSeek: JSON](https://api-docs.deepseek.com/guides/json_mode/):
  финальный `response_format=json_object`, JSON-инструкция и обработка пустого ответа.
- [DeepSeek: keep-alive](https://api-docs.deepseek.com/quick_start/rate_limit/):
  пустые строки non-streaming запроса могут поддерживать соединение; поэтому
  timeout чтения сокета не заменяет общий deadline действия.
- [Mailpit: Docker](https://mailpit.axllent.org/docs/install/docker/)
  и [runtime options](https://mailpit.axllent.org/docs/configuration/runtime-options/):
  постоянная БД, лимиты хранения, loopback-публикация портов на стороне Compose.
- [Mailpit: Chaos](https://mailpit.axllent.org/docs/integration/chaos/):
  Sender/451/100%, управление через API после включения функции при старте.
- [Mailpit: поиск](https://mailpit.axllent.org/docs/usage/search-filters/)
  и [API v1](https://mailpit.axllent.org/docs/api-v1/): поиск Message-ID и чтение письма.
- [SMTP RFC 5321](https://www.rfc-editor.org/rfc/rfc5321), раздел 4.2.5:
  окончательный ответ DATA определяет приём; таймаут ожидания ответа оставляет
  неопределённость. [SQLite transactions](https://www.sqlite.org/lang_transaction.html):
  BEGIN IMMEDIATE сериализует writers; SQLITE_BUSY не заменяется успехом.

Результаты первоначального исполняемого spike SQOCH-21 находятся в приёмке.
В новой среде доступность ключа/модели, образа, API Chaos и точного поиска
проверяется снова. При неуспехе меняется конкретное техническое решение
в пределах согласованных бизнес-границ; прежний прогон не подтверждает
доступность интеграции в новой среде.

# Техническая спецификация Sqoch

Статус: принятая основа реализации, 22 октября 2026 года.
Функциональный владелец — [бриф](brief.md); выполнение и фактические
свидетельства — [план работ](work-plan.md). Этот документ задаёт границы
реализации; manifests, lockfiles и сохранённые результаты команд фиксируют
фактически установленные версии и проверки.

Визуальные требования, компоненты и адаптивность принадлежат
[дизайн-системе «Формуляр с разделами»](design-system.md), выбранной
23 октября 2026 года. Она применяется ко всем экранам и состояниям, сохраняя
функциональные и API-границы этой спецификации и брифа.

## Структура и владение

Один репозиторий и один корневой JS-пакет приложения. В корне нет
`pnpm-workspace.yaml`: служебный генератор должен владеть отдельным деревом
зависимостей. Реализованная структура:

```text
src/
  App.tsx              # подключение единственного потока
  main.tsx             # точка входа React
  styles.css           # стили приложения
  fonts.css            # локальные @font-face, включаемые Vite в CSS
  features/booking/    # controller, форма, сводка, demo, API и тесты
backend/               # Python-приложение, схемы, чистые правила и тесты
tools/openapi/         # независимый пакет генерации типов
e2e/                   # сценарии настоящей связки UI/API
docs/                  # бриф, спецификация, план и свидетельства
```

| Владелец             | Ответственность                                                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| Backend / Pydantic   | Формы данных, строгая валидация, правила сопровождения, цены и итог, OpenAPI, различимые ответы API |
| Frontend / booking   | Черновик, подсказки/ошибки формы, шаги, ожидание, результаты и доступное управление                 |
| API-адаптер frontend | `fetch`, сериализация запроса, распознавание 422/409/транспортной ошибки; типы берёт из генерации   |
| Генератор            | Получение объявлений типов из OpenAPI без runtime-клиента; проверка отсутствия расхождения          |

`Booking` владеет запросами, шагами и фокусом; `BookingForm`, `OrderSummary`
и `DemoControl` выводят локальные части интерфейса без второго хранилища.
Tailwind сканирует только `src` относительно `styles.css`, чтобы посторонние
документы, cache и содержимое checkout не меняли набор генерируемых utilities.
React Hook Form ведёт поля и массив участников; React state — шаги потока.
Для запросов достаточно `fetch`. Локальная валидация помогает покупателю,
но сервер повторяет проверки независимо. Бизнес-правила backend выделяются в
небольшие чистые функции, API связывает их со схемами. Абстракции репозиториев,
Unit of Work, универсальный DDD-каркас и новые framework-пакеты не требуются.

Из Seller Platform применяются принципы явного владельца и границы модуля,
тестируемости и самостоятельной проверки. Для одного потока не нужны
маршрутизатор, глобальное хранилище, TanStack Query, XState, общий SDK или
монорепозиторный оркестратор.

Проверки семантики компонентов, адаптивности, forced colors и загрузки
описаны в [приёмке](acceptance.md). Локальный Lighthouse не заменяет
сценарные проверки браузера и метрики удалённого сервера.

## API и контракт

Все цены — целые рубли (`RUB`), без дробных денежных вычислений. Контрактом
владеют Pydantic-модели; FastAPI публикует OpenAPI. Неизвестные поля тела
запрещены, в том числе клиентские `price`/`total`. Подтверждение не доверяет
прежнему расчёту и не требует сохранённого quote-token: заново валидирует
текущие данные и рассчитывает сумму.

### GET /api/event

Возвращает мок мероприятия:

```json
{
  "id": "sqoch-event",
  "title": "Мероприятие Sqoch",
  "currency": "RUB",
  "max_participants": 4,
  "child_age_limit": 14,
  "companion_min_age": 18,
  "full_ticket_price": 2000,
  "child_ticket_price": 1000
}
```

`id` и `title` — демонстрационные значения, не данные реального мероприятия.

### POST /api/orders/quote

Тело обоих POST имеет одну форму:

```json
{
  "participants": [
    { "name": "Анна", "age": 18 },
    { "name": "Илья", "age": 13 }
  ],
  "email": "anna@example.com"
}
```

Список содержит 1–4 записи. `name` — строка, непустая после trim; `age` —
строго целое число от 0. Boolean, дробь, строка, `null`, пустое и пропущенное
значение не приводятся к допустимому возрасту. `email` обязателен, проходит
валидацию email. Состав с участником младше 14 допустим только при наличии
хотя бы одного сопровождающего от 18 лет; он может сопровождать всех детей в заказе,
соответствие один к одному не требуется. Участник 14–17 лет может идти
отдельно, но не является сопровождающим. Возраст остаётся обязательной
частью обоих POST; композиция формы не вводит предварительного мастера
выбора билетов и не меняет API. Например, 17 отдельно допустим, а 18+13+12
допустимы с итогом 4 000 ₽. Ответ `200` содержит нормализованные данные и
серверный расчёт:

```json
{
  "participants": [
    { "name": "Анна", "age": 18, "ticket_type": "full", "price": 2000 },
    { "name": "Илья", "age": 13, "ticket_type": "child", "price": 1000 }
  ],
  "email": "anna@example.com",
  "total": 3000,
  "currency": "RUB"
}
```

`ticket_type` — объединение `child | full`. Демоисход подтверждения не влияет
на расчёт валидного заказа.

### POST /api/orders

Тело совпадает с quote. Заголовок `X-Demo-Scenario` принимает `success` или
`sold_out`; отсутствие означает `success`. Недопустимое значение заголовка
является ошибкой данных. Успех `201` возвращает поля quote и `order_id` с
непредсказуемым UUID. Это демоидентификатор, сохранение заказа не обещается.

После успешной валидации в режиме `sold_out` сервер отвечает `409`:

```json
{
  "detail": {
    "code": "sold_out",
    "message": "К сожалению, места закончились. Попробуйте другой демосценарий."
  }
}
```

`sold_out` — стабильный машинный код; текст может уточняться. Приложение
показывает отказ как отдельный статус, сохраняет черновик и последнюю
серверную сводку. Для неизменённых данных доступен прямой ручной повтор
confirm; редактирование отменяет сводку и требует нового quote. Это
управляемая имитация, а не гонка за остатками и не изменение глобального
количества мест.

После `409 sold_out` error-уведомление расположено непосредственно у кнопки
повтора, объявляется как alert и получает фокус. Оно явно объясняет, что
заказ не создан, а данные и расчёт остались только на текущей странице.
Для успешного демоповтора нужно выбрать «Успех» и нажать кнопку; одна смена
radio не отправляет запрос и не скрывает результат предыдущей попытки.
Ошибки загрузки мероприятия, расчёта и подтверждения называют своё действие
и доступную кнопку восстановления. При неизвестном результате confirm
интерфейс предупреждает, что сервер мог создать заказ, без категоричного отказа.

### Ошибки данных и соединения

Оба POST возвращают `422` для ошибок полей или состава. Форма —
`{"detail": [{"loc": ["body", "participants", 0, "age"], "msg": "…", "type": "…"}]}`.
`loc` — массив строк/индексов. В ответе сохраняются только сериализуемые
детали; клиент не зависит от Python-объектов в `ctx`. Ошибка состава относится
ко всему массиву участников. Транспортная ошибка, неожиданный HTTP-ответ и
`409 sold_out` различимы и не создают ложного подтверждения.

## Генерация типов: локализованное исключение

Приложение использует нативный TypeScript 7.0.2. Исследованные генераторы
зависят от прежнего TypeScript Compiler API. Отдельный `tools/openapi/`
использует Hey API 0.99.0 и TypeScript 6.0.3 со своими manifest, lockfile и
`node_modules`, вне workspace приложения. Прямые импорты приложения из этого
дерева запрещены.
Разрешение пакета проверено отдельно: приложение использует
`node_modules/.pnpm/typescript@7.0.2`, генератор — собственный
`tools/openapi/node_modules/.pnpm/typescript@6.0.3`.

Генерируются только объявления типов: без SDK, Query, Zod, runtime-кода и
runtime-enum. Frontend API-адаптер использует эти типы, а HTTP-поведение пишет
явно. OpenAPI экспортируется детерминированно из backend; проверка синхронизации
сравнивает схему и сгенерированный файл без перезаписи принятого результата.
Изменение контракта обновляет источник, генерацию и потребителя в одной задаче.

## Состояния frontend

Пользователь видит два этапа — данные и проверка; результат имеет отдельный
статус. Их текущая компоновка определена принятой [дизайн-системой](design-system.md).
Внутренние состояния ожидания и ошибок сохраняют различимые роли:

1. Загрузка мероприятия: ожидание, данные или понятная ошибка с повтором.
2. Данные: 1–4 участника, один email, контекстная обратная связь и запрос quote.
3. Проверка: нормализованный состав, цены и сумма из ответа; редактирование
   участника или email возвращает тот же черновик, сразу отменяет прежний
   quote и задаёт одноразовый фокус выбранному полю.
4. Подтверждение: один незавершённый запрос; повторный клик заблокирован.
5. Результат: подтверждённый заказ либо `sold_out`. Успех показывает число
   участников и сумму из ответа confirm перед полным `order_id`.
   `sold_out` сохраняет видимой последнюю серверную сводку; ручной повтор
   отправляет те же данные напрямую в confirm. Транспортный сбой остаётся
   отдельной ошибкой с сохранёнными данными и возможностью повторить действие.

Нельзя подтвердить отменённый/старый расчёт. Изменение состава, в том числе
удаление сопровождающего, требует нового расчёта и новой валидации. UI не
считает отсутствие HTTP-ошибки доказательством успеха без ожидаемой формы
ответа. Автоматические повторы подтверждения не нужны. Черновик живёт в памяти
страницы; `localStorage` и серверное хранение не вводятся.

### Локальные подсказки и восстановление

Подсказка тарифа использует валидный введённый возраст и данные мероприятия;
пустое значение не получает тариф и не превращается в 0. Для помощи/статуса
участника и заголовка заранее резервируется место по дизайн-системе; длинные
ошибки переносятся и увеличивают область, не скрывая текст. Общее пояснение
правила сопровождения имеет постоянные текст и зону; ошибка состава по-прежнему
проверяет текущих участников. Действие «Добавить участника» сохраняет название
при любом возрасте, доступно при количестве меньше 4, добавляет пустые имя и
возраст после существующих строк и фокусирует имя новой строки. Оно не
придумывает возраст сопровождающего и не заменяет проверку состава.
Локальные подсказки не являются источником итоговой суммы:
проверка, `sold_out` и успех показывают только полученный серверный расчёт.
Демопереключатель расположен на проверке перед подтверждением и при
`sold_out` перед прямым повтором; на этапе данных он не нужен. Это меняет
размещение элемента, сохраняя значения и семантику `X-Demo-Scenario`.

Локальная форма поддерживает одну отмену последнего удаления заполненного
участника с актуальными значениями и исходной позицией. Следующая операция
добавления/удаления или успешный quote завершает возможность отмены; неудачный
quote её сохраняет. Краткое локальное уведомление содержит одно действие
отмены на месте удалённой строки; его доступное имя начинается с видимого
«Вернуть». Все поля заранее обозначены обязательными, сохраняется `noValidate`
и единая собственная валидация. Фокус после структурных действий, адресного редактирования и отказов
применяется однократно после готовности DOM и разблокировки controls.
При повторной неудачной загрузке мероприятия фокус возвращается на Retry,
связанный с описанием ошибки; исходный отказ загрузки фокус не перехватывает.

Общий deadline 15 секунд покрывает fetch и чтение body; отмена при unmount
прерывает активный запрос, поздний результат не меняет состояние. Сеть,
таймаут, 422 и sold_out имеют разные роли. Потеря ответа confirm не доказывает,
что заказ не создан. Ошибка сервера или некорректный ответ confirm также не
доказывают отказ: сохраняются сводка и неизвестный результат, повтор только
ручной. Некорректный ответ quote остаётся обычной ошибкой расчёта.
Автоматического повторения нет. После `sold_out` смена
демосценария не меняет состав и расчёт: прямой ручной повтор confirm не
требует прохода через экран проверки или нового quote. Редактирование
участника/email отменяет quote и закрывает этот путь до нового расчёта.
HTTP-методы, тела, статусы и заголовок demo не изменились. Повреждённый ответ
422 без непустого корректного массива `detail` не считается доказанной ошибкой
полей: confirm сохраняет сводку и неизвестный результат; quote остаётся на форме.

## Локальный запуск и качество

Vite обслуживает frontend на 5173 и проксирует `/api` в FastAPI на 8000.
`pnpm dev` запускает оба процесса с reload; Ctrl+C завершает их. Готовая сборка
попадает в `dist/`, и backend раздаёт её одним процессом, если каталог есть.
API и его тесты работают независимо от frontend-сборки. Запуск и команды —
в [README](../README.md); Docker, БД, секреты и приватные инструменты не нужны.

`pnpm run setup` устанавливает frozen JS и locked Python из публичных реестров.
Шесть операций `agent-platform.json` — декларативная карта обычных команд
`package.json`, без внешнего Kit или launcher. `verify` объединяет типы,
линтеры, форматирование без записи, синхронизацию контракта, тесты, сборку,
реальные E2E и ссылки документации. Markdown checker проверяет локальные
inline-ссылки и изображения, но не anchors; он не пропускает отсутствующие
приватные файлы как якобы доступные.

## Осознанные ограничения

Нет хранения заказов, реальных остатков, оплаты, писем и авторизации.
Для продакшена потребуются самостоятельные решения; в тестовое задание они
не входят. Настройки HTTPS, сжатия и cache TTL проверяются на выбранном
хостинге. Известное предупреждение Starlette/HTTPX TestClient не подавляется
и не исправляется добавлением новой зависимости в рамках этого проекта.
